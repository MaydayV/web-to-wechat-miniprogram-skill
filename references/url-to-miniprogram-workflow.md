# URL / Web 项目迁移工作流

按任务大小抽取必要步骤；小型单页可合并盘点和映射，但不要跳过真实行为与小程序约束检查。

## 分层网站盘点与独立视觉

先把网站当成可分析的结构与功能来源，按层取证；不要把“打开浏览器看每一页”当作默认扫描方式。

### 静态优先的盘点顺序

1. **入口与可访问范围**：读取给定 URL；同源检查 `robots.txt`、`sitemap.xml`、规范链接和首页可见导航。遵守站点访问限制，不遍历猜测路径、不绕过权限，也不并发暴力抓取。
2. **路由层**：从 HTML 中提取同源链接、表单 action、meta/canonical、内嵌 JSON、SPA 初始状态及公开路由配置；有用户提供源码仓库时直接查 Router、页面组件和跳转处理器。将发现的 URL 归一化、去重并按用户流程分组。
3. **页面/组件层**：提取标题、语义区块、表单字段、按钮/链接作用、条件容器、分页、列表数据和页面之间的参数传递。对压缩 JS 只定位路由、事件、状态和 API 线索；不把源代码、JS bundle 或资源复制到小程序。
4. **数据/API 层**：从公开源代码或无需登录的页面请求中记录接口路径、方法、参数和字段证据。只保留完成迁移所需的脱敏结构，不保存 cookie、token、真实个人数据或敏感请求体。
5. **状态/流程层**：把控件与状态写成 `入口 -> 输入 -> 校验 -> 操作 -> 结果/失败 -> 保存/返回`。把静态证据、运行时观察、推断和未知分列，不从界面外观猜业务逻辑。
6. **浏览器补查**：仅对静态读取无法确认的点使用浏览器，例如客户端渲染后的路由、下一步按钮状态、必要的弹窗/分支、响应式下控件显隐。每次只验证一个具体假设，使用合成、非敏感输入；无需截图时不截图，确认后停止。

URL-only 网站通常先通过公开站点地图、HTML 和链接覆盖路由与功能骨架；交互结果依赖客户端状态时再做最小 GUI 观察。若静态分析拿不到 JS 状态或 API 契约，把信息标未知，不用更多浏览器点击或猜测填补。

### 功能参考与视觉隔离

把参考站作为产品研究材料，提炼它服务的用户、待解决的问题、主题方向、核心任务、输入/反馈机制和可改进的体验。基于这些线索形成独立的小程序概念，可以保留高层功能（例如自我探索问答、进度、个人总结），但题目、计分、文案、品牌、资源和交互细节应原创或由用户提供授权资料。迁移蓝图不要记录可直接照搬的色值、字体、间距、圆角、阴影、图标、插画或动效；不下载/复制站点资源到小程序。

为“更好”写清至少一个面向用户的改进点，例如降低作答负担、允许保存并继续、把结果变成用户可编辑的个人总结、改善隐私控制或让关键后续操作更清晰。不要仅换皮；也不要以参考站的特色页面构图和文案作为设计起点。

来源路由不等于小程序页面数。多工具网站先按用户任务分组，用首页/hub呈现常用入口和状态；有独立表单、数据、校验或多步流程的工具保留专属页面。将来源站的长说明改写为原创、简短、行动导向的中文文案；必要的安全、隐私、资格与限制说明不能为缩短而删掉。

多页面或创意转化任务可用这张表把灵感与实现隔开：

| 参考线索（概述） | 对应的用户需求 | 保留的高层功能 | 原创实现 | 改进点 |
| --- | --- | --- | --- | --- |

只记录概念和功能，不复制来源站的题目、文案、图像或视觉 token。

小程序视觉按以下优先级重新确定：

1. 用户已有的小程序设计系统、品牌规范与组件库。
2. 用户明确提供的新品牌/视觉要求。
3. 前两者都没有时，采用原创的微信原生视觉：清楚的页面层级、原生导航与安全区、适合触屏的表单和状态反馈；视觉基线由本项目自行确定，不从参考站取样。

验证只对照功能流程和信息是否完整，不以源站截图作像素还原目标。浏览器截图只用于判断源站元素是否出现、操作后状态是否变化；不能据此复刻其视觉系统。

## 快速模式：工具网站 URL -> 原生小程序

用户给出网站链接并明确要转换时，按此短链推进，避免反复要求用户讲解页面：

1. **确认目标代码**：在当前工作区找到既有小程序及 `miniprogramRoot`；没有时沿用仓库约定创建原生目录。先检查工作区改动，禁止覆盖无关变更。
2. **静态盘点主要操作**：先查页面、导航、公开脚本和接口线索，整理典型输入、处理动作、结果与复制/下载/分享/保存/历史/导出动作。只有静态证据不足时，才在浏览器验证一个核心操作；不要触发真实付费、删除、对外提交或发送敏感信息。
3. **快速盘点范围**：检查首页/工具导航以及核心流程可达的页面和状态；再用路由、链接、事件跳转、条件视图交叉核对。先锁定用户要转换的工具功能，营销页和无关后台不自动纳入。
4. **直接实现**：从主工具流程开始，用现有项目的原生页面和组件完成“输入 -> 处理 -> 结果 -> 后续动作”，再实现范围内其他工具。复用表单字段、校验提示、结果卡片、历史列表、空/错误状态和请求层。
5. **按核心闭环验证**：编译后先运行最重要的工具流程，再覆盖主导航、必要输入边界、失败和二次进入。若只能静态检查或 DevTools 不可用，准确说明，不用更多设计确认代替验证。

可以根据实际界面快速识别常见工具类型及需要观察的行为：

| 网站形态 | 核心操作优先级 |
| --- | --- |
| 计算/评估 | 字段、单位、必填和范围校验、计算规则证据、结果解释、重算与结果保存/分享 |
| 转换/生成 | 输入内容、参数选择、格式/大小限制、进度、结果预览、复制/下载/重新生成 |
| 查询/数据面板 | 查询条件、筛选/排序、分页、详情、刷新、无结果和接口失败 |
| 清单/任务工具 | 创建/编辑/完成、状态变化、排序、离开后恢复、重复操作 |
| 内容/模板编辑器 | 编辑状态、实时预览、撤销/重置、保存、导出或分享 |

这些类型只用于提醒检查，不用于推断产品规则。实际流程以可访问页面、源码、API 契约或用户确认的事实为准。

## 登录受限页面与浏览器操作

是否需要控制浏览器取决于站点和任务，不是每个 URL 都要开 GUI：

- 公开静态页面先用页面读取或源码检查；若页面是 SPA、操作状态不在初始 HTML、需要填写表单才能看到结果，再用浏览器实际交互。
- 需要用户登录后才可见时，只在用户明确授权检查该站点/账号且该访问本身被允许的情况下查看。优先使用用户已登录的受控浏览器；否则请用户在可见浏览器中自行输入账号、密码、短信码、验证码并完成登录，完成后再继续。不要索取、读取、记录或代填这些秘密，也不要绕过 MFA、验证码、付费墙、访问控制或反自动化措施。
- 浏览器自动化只检查用户指定的功能页面和必要流程，不翻看无关个人资料、消息、其他用户记录或账户设置；不批量下载真实用户的答卷、报告或历史记录。需要验证页面状态时使用用户自有测试账号和合成答题数据。
- 页面可见、用户已登录，不自动等于拥有复制站点内容或转用题库/品牌/算法的权利。对来源权利不明确的题目、量表、图片、文案和计分模型，不复制到新小程序；请用户提供自有授权材料，或只复用交互模式并改用有权使用的内容。
- 在本地笔记或实现中只保存必要的字段和观察结论。不得保存 cookie、token、完整 URL 中的会话参数、个人答题记录或可识别身份信息；网络观察只保留脱敏后的接口路径和结构证据。

浏览器检查记录应区分：**公开可见**、**用户授权后可见**、**用户提供材料**、**仍无法确认**。登录受限导致关键流程无法观察时，把它列为阻塞并提供用户可补充的材料选项，不把访问失败当成源站不存在该功能。

## 心理测评类网站专项盘点

心理测评站不只是问卷 UI。围绕“选测试 -> 阅读说明 -> 作答 -> 计分 -> 查看结果 -> 保存/分享/复测”记录完整流程及证据：

| 模块 | 需要观察 |
| --- | --- |
| 测试入口 | 测试目录、分类、适用人群说明、题数/时长、开始条件 |
| 作答流程 | 单选/多选/量表/文本题、必答规则、进度、上一题/下一题、跳题/分支、退出后恢复 |
| 计分规则 | 正反向题、维度映射、加权/归一化、缺失答案、分数区间和边界条件；每项都要有源码、官方说明或用户提供规则作证 |
| 结果页 | 维度分数、区间标签、解释文案、建议、风险提示、复测入口和分享形式 |
| 账户与数据 | 是否登录才能测试/看结果/保存历史；答案、分数和报告存在哪里，能否删除/导出/撤回分享 |
| 失败状态 | 未答完、重复提交、网络失败、结果缺失、登录过期、保存失败和重新计算 |

**计分与解释是关键业务逻辑，必须精确复现已证实规则，不允许从几份答案与结果反推公式后直接上线。** 如果页面只显示题目和结果样例、但看不到规则或受控 API，标记评分为待确认；请用户提供量表授权、计分表/算法说明或可用于本项目的正式 API 契约。不得把临床诊断、风险结论或疗效建议包装成普通娱乐分数，也不得根据测试结果自行产生诊断结论。

数据验证优先使用虚构账号和合成答案。只验证本项目需要的最小数据字段和生命周期；不要把源站真实用户答卷复制进小程序。对涉及心理健康、身份信息或私密回答的功能，实施前确认必要的数据用途、存储期限、访问范围、删除/导出路径和用户告知方式。

如果用户只要求把公开页面做成原生界面，可以先完成入口、答题控件、进度与结果布局；计分结果在规则未确认前不得伪造成真实结果，应明确标为未接入/演示态，或等待用户提供规则后再完成业务闭环。

### 原创自我观察与验证量表的边界

- 用户只借鉴选题/核心功能、希望开发原创产品时，可以设计原创的生活体验问题和个人总结；必须明确标成自我观察或反思工具，不计算临床分数、不筛查、不诊断、不声称经过心理测量验证。
- 原创问题只描述可观察的生活场景与用户偏好；总结只归纳用户自己选择的内容，不从答案推断诊断、风险、概率或所属群体。
- 用户要求保留经验证量表、标准分数或诊断解释时，必须使用有权使用的正式题目、语言版本、适用人群、评分规则和研究/专业依据；不从参考网站少量样例推导，不把翻译当作已验证量表。
- 对心理/健康答题数据，默认先考虑本机处理和最少收集；需要账户、云端历史或分享时，确认数据用途、存储、访问、删除及明确告知。

## 1. 读取来源

- **用户提供 URL**：优先通过可用的 HTTP/页面读取方式、站点地图、同源链接及公开 HTML/脚本梳理路由和功能结构。只有需要确认动态状态时才开浏览器；截图只用于核实元素或状态，不用于参考站视觉还原。不要只依赖搜索摘要、单张截图或页面源代码。
- **用户提供 Web 仓库**：先检查工作区状态、README、路由定义、页面组件、事件/状态代码和请求层。只为功能适配检查必要的响应式行为，不抽取视觉 token 作为复用目标。页面运行效果与源码不一致时分别记录。
- **已有小程序**：先检查 `project.config.json`、`app.json`、`miniprogramRoot`、目标页面、公共样式、路由、请求封装和组件库。沿用已存在结构，不建立平行架构。
- URL 与源码都提供时，以源码了解状态和接口，以可运行页面校对实际表现；把版本差异列出来。

登录后内容、需付费页面、地理/设备/账号条件页面，只有在用户已提供并授权使用的访问路径下检查。不得尝试绕过身份或反爬限制。

如果网页适配了手机和桌面，检查至少一个常用手机视口及当前能访问的主要布局；迁移时保留信息优先级和关键动作，重新按微信单列/滚动/安全区组织，不照搬桌面导航和多栏缩放。

## 2. 建立页面与功能清单

按页面/路由整理以下信息，事实与推断分开。页面清单通过四类证据交叉检查：路由配置、站内导航目标、事件处理器中的跳转、条件渲染或单 HTML 中显隐切换的视图。URL-only 时从可公开读取的链接、脚本和初始状态提取这些线索。源码中可能未链接的路由也要识别；动态权限态或未能打开的视图列为待确认，不能宣称覆盖。

| 项目 | 记录内容 |
| --- | --- |
| 路由与入口 | URL/path、进入方式、返回/分享关系、需要的参数 |
| 页面骨架 | 顶部、内容区、列表/卡片、底部操作、固定/滚动区域 |
| 信息结构 | 区块职责、阅读顺序、必要的信息密度、移动端功能可见性；不提取源站视觉 token 供复用 |
| 交互 | 点击、表单、校验、排序筛选、弹窗、分页、手势、加载反馈 |
| 状态 | 初始、加载、成功、空、失败、禁用、未登录、无权限、离线 |
| 数据与 API | 请求方法、路径、参数、响应字段、分页/错误语义、身份要求；未知标注未知 |
| 功能依赖 | 上传/下载、地图、视频、图表、第三方 SDK、浏览器专属 API；记录功能需求，不复制来源站素材 |

做一张流程图或有向清单，说明主要用户任务从入口到完成如何跨页。只记录目标范围中的关键任务，避免把网站所有营销页和管理页无差别搬入小程序。

## 3. 建立迁移蓝图

多路由迁移或多阶段实施时，维护一份迁移蓝图作为单一事实来源，至少包括页面清单、Tab/子页面分类、跳转关系、组件复用、独立的目标设计决策、交互状态、数据/API 依赖、资源替代方式和逐项验证结果。不得把参考站视觉 token 写入蓝图作为实现目标。蓝图必须体现已确认内容与待确认项，不把推断写成决定；页面范围或设计决策变化时同步更新。单页修改、只读分析或用户明确不需要文件时，不额外落盘。

新项目可以把小程序骨架放在 Web 源码旁的独立目录，但先检查用户已有仓库约定和小程序根目录；不可一概强制创建名为 `miniprogram/` 的嵌套目录。已有小程序内则复用当前真实根目录。

## 4. 作出小程序适配决策

为每个网页能力选择一种结果：**原生映射**、**替代实现**、**降级/移除**、**依赖后端/权限待确认**。

| Web 形态 | 小程序候选 | 检查点 |
| --- | --- | --- |
| 路由与链接 | `app.json` 页面、`navigateTo`/`redirectTo`/`switchTab`、分享路径 | tab 页面跳转限制、冷启动参数、返回栈 |
| DOM 结构 | WXML 视图/列表/表单/自定义组件 | 组件层级、列表 `wx:key`、事件绑定与可访问点击区 |
| 网页布局行为 | 项目组件与独立设计的 WXSS | 只保留内容关系和必要的移动端功能行为；颜色、字体和视觉 token 重新设计 |
| 表单与校验 | 小程序表单控件和页面状态 | 键盘、焦点、校验时机、重复提交、错误反馈 |
| HTTP/fetch | `wx.request` 封装或项目请求层 | 合法域名、HTTPS、超时/取消、鉴权、分页和错误码 |
| Local/session storage | `wx.setStorage` 或页面状态 | 生命周期、清理、跨端共享要求、敏感数据避免落盘 |
| Cookie/session | 已确认的小程序身份/API 方案 | 不伪造浏览器 Cookie；需后端确认认证与续期契约 |
| 上传/下载 | `wx.chooseMedia`、`wx.uploadFile`、`wx.downloadFile` | 临时路径、权限说明、上传失败和服务端校验 |
| 浏览器 API | 微信平台对应能力或明确降级 | 分享、剪贴板、定位、相机、文件、支付均查当前官方规则 |
| 动画/第三方组件 | WXSS 动画、已有小程序组件或本地资源 | 不依赖 DOM、hover、WebGL、远程字体/CDN 的核心体验 |

功能迁移保留必要信息顺序和任务闭环，但视觉必须重新设计。建立每路由的页面/组件映射和每条核心交互的状态迁移，避免只做静态截图界面。

| Web 结构/事件 | 原生小程序实现 | 注意 |
| --- | --- | --- |
| `div`/`section`/`main`/`header` | `<view>` | 按任务重新组织层级，不照搬源站布局 |
| `p`/`span`/标题文本 | `<text>` 或 `<view>` | 按本项目排版规则重新设计 |
| `img` | `<image>` | 设置显示尺寸；用自有或获授权的新资源，不复制源站品牌图 |
| 内部 `<a>` 路由 | `<navigator>` 或页面导航 API | Tab 页使用正确的 tab 导航方式；不把外部站点塞进 WebView |
| 表单与输入 | `<form>`、`<input>`、`<textarea>`、`<picker>`、`<radio-group>`、`<checkbox-group>`、`<slider>` | 按字段语义选择控件，重做校验、键盘和错误状态 |
| 数组 `.map()`/列表 | `wx:for` + 稳定 `wx:key` | 列表身份需稳定，不用展示顺序索引代替业务键 |
| 点击/输入/值变化 | `bindtap`、`bindinput`、`bindchange`；需阻止冒泡时用 `catchtap` | 明确事件目标、数据参数和重复提交状态 |
| React/Vue/JS 页面状态 | 目标框架的状态模型；原生页面用 `Page.data`/`setData` | 保留状态转换，不照搬浏览器全局变量或不必要的全局状态 |
| `localStorage`/Cookie/Fetch | 经确认的本机存储、身份方案与 `wx.request` 请求层 | 不假定 Cookie 可迁移；敏感答案/账户数据先定保存与清理策略 |

CSS 不做整表机械转译，也不以 `px -> rpx` 的全局替换生成新视觉。只依据功能确认触控区域、滚动/固定行为、安全区和窄屏约束，然后按独立设计系统编写 WXSS。跨端 API 行为或基础库限制应按当前官方文档核对。

### 小程序脚手架核对

开始加页面前先定位仓库根目录和真实 `miniprogramRoot`，核对 `project.config.json`、`app.json`、项目框架、现有路由/分包和共享组件。已有工程不另建第二套平行小程序目录。

- 新增/注册每个原生页面时核对同路径的 `.js`、`.json`、`.wxml`、`.wxss` 文件；新增组件时核对组件配置与文件集合。
- `app.json` 的页面/Tab 声明、导航调用和实际文件路径必须一致；仅保留功能范围需要的页面。
- 复用项目已有请求、存储、组件和主题约定。若已有工程没有视觉规范，另建原创的原生设计基线，不提取来源站 token。
- 首次或大幅改变页面结构后，做一次静态产物检查，确保入口、路径、文件集合和打包根一致；不要凭开发者工具当前打开的项目名判断根目录。

若 DevTools 报告错根目录、模板残留或编译模式错位，按可见报错和 Git 状态定位后再修；先保护/恢复受跟踪文件，删除生成残留只限于能确认的文件，不做目录级清扫。

## 5. 发现数据与 API 需求

盘点页面数据来源，识别潜在接口场景：列表、详情、筛选、分页/加载更多、表单提交、状态变更、聚合统计；也留意配置字典、文件上传、用户身份等依赖。对每个候选记录源代码/网络观察证据、页面使用字段、方法/路径/参数/成功与错误响应（可获得时）、鉴权与分页语义。

这些场景只是**接口需求线索**，不是可直接编码的 API 设计。只根据数组、筛选函数、Toast、“成功”文案或页面外观推测出 endpoint 时，标为 `待确认`，不能自动替服务端决定 URL、HTTP 方法、响应字段、权限或写入语义。优先追踪源站代码中的真实 API 调用、公开文档或用户提供的后端契约；缺失的契约要向用户/后端负责人确认。

页面分离后，让页面只管理展示状态和交互，业务 API 放入现有或新建的模块层，通用请求层集中处理 base URL、鉴权、超时和错误映射。不要仅凭页面操作形态自动生成 endpoint。

当用户要求接口正式化、且项目需要可追踪契约时，再把已证实的接口提升为 `contract`/OpenAPI 单一事实源，并交叉校验页面调用、契约、文档和当前平台可用的测试适配器；有版本迭代时记录接口差异。不要为单纯的原生 UI 迁移生成治理文档或装依赖。MSW 适用于 Web，不可直接当作微信小程序 Mock 方案。

## 6. 处理信息缺口

- 若网站源码和 API 合约可用，复用已确认的数据模型与服务，不复制网站的浏览器登录机制到小程序。
- 若只有 URL，能观察到的匿名体验可以实现；需要登录、提交、支付、账户数据或持久化的功能，先确认小程序身份方式、API 是否可用、请求域名配置及错误契约。
- 静态原型的数据可在用户接受明确的演示态时集中放置；生产路径不得以固定数组、Toast、“成功”提示或硬编码响应冒充真实后端操作。尚无后端时，标明“待接 API”并保证不制造成功假象，或只实现可独立完成的本地流程。
- 价格、评分、资格、法律/医疗表述、权限和数据保留规则属于高影响信息，不按页面样例推测。

## 7. 实施和回归

1. 从一个最小完整用户闭环开始：入口 -> 主要查看/输入 -> 成功或可理解的失败 -> 返回/再次进入。
2. 新页面按现有项目声明路径和配套文件；更新 `app.json`、导航/分享参数、组件引用和打包资源。
3. 将复用逻辑放在当前架构认可的位置；保持 API、页面展示状态和表单状态职责清楚。
4. 检查原网页中缺席但小程序必须处理的情况：冷启动、前后台、拒绝权限、无网、请求超时、重复点击、空结果、长列表、键盘遮挡、安全区。
5. 运行项目已有静态产物校验和微信开发者工具 CLI 编译/`preview`（若可用）。先读 CLI 自身帮助；需要时用 `open` 建立 IDE 连接并取其报告的当前端口，再跑 `preview`。检查退出码、错误输出和生成物；工具/账号/AppID 阻塞应归为宿主问题，不误报成应用缺陷。
6. 若 CLI 通过但动态交互仍有问题，再做单路由 GUI 冒烟：先确认 DevTools 已连接，再检查当前路径、关键控件、一个主要动作及运行时异常。优先看结构化 report/trace；截图只用于确认功能状态或用户明确要求的视觉检查，不用来对照源站风格。
7. 若 DevTools 导入错根目录、模板污染或编译模式失配，先对照 Git 状态和配置定位来源；只修有明确证据的仓库级问题。清理生成文件前先保护/恢复跟踪文件，不批量删除未知目录。
8. 分别报告静态检查、编译/预览、模拟器、真机或体验版证据。没有做的步骤写“未验证”。

对工具型网站优先完整走通最主要的一条真实任务链，再按用户要求补其他功能；不要因图片差异或可逆样式决定暂停主流程。复制、下载、分享、历史/收藏、重置等网站上的主要后续动作也要盘点，判断是否属于转换范围。
