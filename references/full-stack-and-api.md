# 小程序全栈与 API 工作流

当功能依赖真实数据、登录、提交、保存、上传或计算服务时读取本指南。纯静态页面、独立本机工具不必为完整性而增加后端。

## 1. 先确认系统边界

区分三个工程对象：参考网站、目标微信小程序、为功能服务的后端。它们可能在同一仓库，也可能是不同仓库或外部服务。修改前分别检查工作区状态、README/部署文档、路由/页面、请求层、服务端入口、配置和数据库结构；不从仓库名称推定实际运行架构。

按真实调用链追踪每个功能：

```text
页面事件 -> 页面/状态处理 -> API 模块 -> 公共请求层
          -> 服务端路由 -> controller/service -> 数据模型/数据库/外部服务
```

每段都记录文件位置和证据。前端找不到对应后端接口时标记为“未发现/待确认”，不要按 endpoint 命名惯例直接创建新接口。

## 2. API 需求与现有接口盘点

先搜索项目已有请求调用和封装，例如 `fetch`、Axios、`wx.request`、React Query/SWR 及 `api/`、`services/`、`request/` 目录；再追踪到服务端路由和数据层。通过功能线索补查常见接口类别：

- 列表、详情、搜索/筛选、分页和统计。
- 表单创建/更新、状态变更、删除或批量操作。
- 登录/用户资料、上传/下载、生成或长任务。
- 权限、租户/用户归属、重复提交、并发及幂等处理。

每个真实或候选接口记录：调用位置、方法、路径、请求字段、成功/错误结构、鉴权方式、分页/幂等规则和证据来源。分清“源码实际调用”“公开文档”“用户提供契约”“界面推断”。界面推断的字段和 endpoint 必须标为待确认。

URL-only 时可从公开页面及授权的浏览器运行状态观察请求元数据；不可读取、保存或复用 cookie/token、真实用户请求体、会话 URL 参数和个人数据。静态网页显示一个按钮，不足以证明接口、响应字段或写入规则。

## 3. 前端 API 层与微信接入

优先复用目标小程序的请求封装、数据模型和状态管理；没有时按项目惯例分离：

- 公共 request 层：base URL、超时、鉴权注入、统一错误映射、取消/重试策略。
- 业务 API 模块：按用户功能分组，集中封装路径、参数与响应结构。
- 页面：只管理交互状态和展示，不散落 URL、凭据或重复网络逻辑。

接入现有 Web 服务前确认 HTTPS、微信服务器域名配置、部署环境和 API 权限。网站 Cookie/浏览器 session 不会自动成为小程序身份方案；若需微信身份，按官方文档设计服务端 code 换取与 token 生命周期，所有秘密只留服务端。不得把 `AppSecret`、`session_key`、支付密钥或 API Key 写进客户端。

需要上传、下载、支付、定位、剪贴板、分享等平台能力时，先核对当前官方 API、基础库最低版本、用户授权和失败路径；给用户说明权限与数据去向。不要复制 Web 登录、支付或存储实现后假设它可在小程序运行。

## 4. 何时调整后端

后端改动仅在完整用户闭环确实需要、并且用户授权当前任务进行实现时纳入范围；先检查现有服务架构和数据模型，再做最小兼容变更：

1. 保持现有路由、领域规则、认证和迁移约定；不要为接小程序另起一套平行后端。
2. 新 endpoint 必须有已确认的请求/响应/错误契约；对不确定字段、所有权和规则先标待确认。
3. 对写入在服务端校验类型、范围、身份、资源归属、重复请求和并发；客户端控件不构成安全校验。
4. 数据库变化使用项目现有迁移机制，说明回滚和兼容策略；不直接执行线上迁移或生产发布，除非用户明确要求。
5. 不默认新增云环境、数据库、第三方账号或付费服务。若必须新增，先给出成本/权限/运维影响与替代方案。

## 5. 静态数据、Mock 与正式服务

可以从硬编码数组、页面 `useState`/`data()`、分页变量、按钮 handler 或统计常量发现“可能需要数据服务”的地方，但这些只是候选需求。

- 生产路径不得用固定数据、Toast、“成功”提示或永远通过的本机状态冒充真实 API。
- 没有后端时，如果是明确的本机功能，可实现清楚标注的本地持久化；若功能本质依赖远端协作/账户/数据，则标记待接 API，不伪造闭环。
- 只有用户明确要求演示模式时才加入 Mock，并让 Mock 与正式 API 有清晰切换边界。MSW 不能直接运行在微信小程序中。
- 页面 API 改造与接口治理分开：通常只需实现现有契约；用户要求接口治理时，再使用 `contract`/OpenAPI 作为单一事实源，确认推断字段，并校验契约、实际调用、文档和平台可用的测试适配器。多次版本迭代时生成接口差异。

## 6. 全栈验证

按改动层运行项目已有 gate，不把前端编译通过当作全栈完成：

| 层 | 需要核对 |
| --- | --- |
| 静态结构 | 页面/组件文件集、`app.json`、`miniprogramRoot`、请求引用和配置 |
| 前端/API | 参数、成功/错误状态、加载、空数据、超时、重复提交和权限失败 |
| 后端 | 路由/service/数据库契约、服务端验证、认证与资源归属 |
| 联调 | 使用获授权的开发/测试环境与合成数据，核对请求/响应和域名 |
| 小程序运行 | CLI 编译/预览；动态交互问题再做窄范围 GUI/模拟器验证 |

明确区分本机静态检查、mock/local API、开发环境联调、开发者工具/模拟器、真机及部署后验收。没有真实部署时写“未做部署验收”。绝不为测试提交真实心理、医疗、支付或其他敏感数据。
